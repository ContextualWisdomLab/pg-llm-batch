# Product / Technical Gap Baseline

This document records commercial-development gaps owned by `pg-llm-batch` or materially gating its release. It is a code-current decision/evidence ledger, not a substitute for live PR, check, review, release, or protected-ref reads.

The active Context Fabric consumer-readiness stack retains PostgreSQL-backed durable lifecycle intent, tenant/RLS isolation, replay identity, and provider-neutral `BatchInferencePort` ownership in this repository. Mutable sibling heads are candidate evidence only; production integration may consume compatible immutable released contracts through a pg-owned anti-corruption layer.

## Canonical product boundary

`pg-llm-batch` owns durable/asynchronous LLM batch preparation, token/size accounting, provider-neutral batch lifecycle ports, PostgreSQL persistence, tenant/RLS isolation, recovery evidence, result ingestion, and the local outbox used to commit privacy-minimized lifecycle publication intent with product state.

Provider/model discovery, routing, fallback, and credentials remain outside this bounded context. Context Graph / Context Fabric integration may consume only compatible immutable released contracts. Mutable sibling branches, source copies, and cross-service SQL are not production authority. PR #323 separately owns the commercial PostgreSQL driver migration, including shared database-driver code; this stack does not overwrite that lane.

## Integrity decision trace: exact durable outbox row shape

**Problem.** `CREATE TABLE IF NOT EXISTS` can leave an existing relation in place. The structural admission guard already rejected missing or incompatible required columns, but a stale or manually altered table could still carry an additional live user column. PostgreSQL would then accept migration success even though the durable aggregate had acquired state outside the package-owned schema. An undeclared nullable column may look harmless to current SQL, but it creates an ungoverned persistence surface for future code, restore tooling, manual operations, or sensitive data.

**Constraints.** Preserve existing canonical rows, transactionality, package/Docker migration parity, and idempotent reapplication. Do not auto-drop an unknown column because the package cannot prove its legal or operational disposal semantics. Do not relax the existing required-column, default, PK, RLS, CHECK, UNIQUE, or index guards.

**Alternatives.** Ignoring additive columns was rejected because the outbox is the canonical durability boundary and purpose-bound data minimization requires the stored shape itself to be explicit. Automatically dropping unknown columns was rejected as destructive and potentially irreversible. Maintaining a second allow-list outside migration SQL was rejected because it would create another mutable schema authority.

**Decision.** Migration 0008 now requires exactly 14 live positive-numbered, non-dropped user columns after proving the 14 named expected columns and their structural properties. Because both conditions must hold, the check detects both missing/incompatible required columns and unexpected additive columns. Any mismatch raises the existing fixed `lifecycle outbox structural schema mismatch` error before later constraint/index repair.

RED `76c5b0001d178625275ee8c16afbca5b7720b70a` modifies a real PostgreSQL table with an `undeclared_payload` column and requires reapplication to fail. Causal SQL fix `f12e9b220ca4e2a32d6f0d6e4254251796eb06d2` adds the exact live-column-count invariant; `47542d6e826bfbec88981c346782b4384d2918ab` mirrors the same SQL bytes into the container initializer; `d84c2af4276ddc80b5827855e0a565a2b87c0bf1` adds a static regression so the catalog contract cannot silently disappear when no integration database is available.

**Effect.** Successful migration now admits only the package-declared durable row shape rather than an arbitrary structural superset. This is a schema/data-authority guarantee, not proof that a privileged database administrator cannot mutate the database. It also does not justify deleting unknown production data; mismatch remains a fail-closed operator repair condition. Hosted exact-head PostgreSQL execution is required before this repair is called GREEN.

## Integrity decision trace: lifecycle column collation authority

**Problem.** PostgreSQL records a column's effective collation independently of its data-type OID. The previous structural admission guard compared `atttypid`, nullability, defaults, generation/identity state, and row shape but not `pg_attribute.attcollation`. A restore or manual `ALTER COLUMN ... TYPE text COLLATE ...` could therefore keep every checked property while changing comparison semantics used by tenant/evidence equality, unique indexes, policy predicates, and text validation. PostgreSQL 18 documents `attcollation` as the defined collation of a column and `pg_type.typcollation` as the type-level collation authority, normally `DEFAULT_COLLATION_OID` for collatable base types (PostgreSQL Global Development Group, 2026k, 2026l).

**Constraints.** Preserve a canonical store without silently rewriting data or rebuilding indexes in a migration whose authority is schema admission. The invariant must also work for non-collatable columns, whose collation OID is zero. Package and Docker migration bytes must remain identical, and successful ordinary reapplication must stay DDL-free for this guard.

**Alternatives.** Ignoring collation was rejected because exact SQL type equality does not imply comparison-semantics equality. Auto-converting a drifted column back to default collation was rejected because `ALTER COLUMN ... TYPE ... COLLATE ...` can require data/index work and can change equality/order behavior; that requires explicit operator reconciliation rather than hidden migration repair. Hard-coding a specific collation OID or locale name was rejected because the package must remain portable across valid PostgreSQL database locales.

**Decision.** For every declared column, migration 0008 now requires `pg_attribute.attcollation` to equal `pg_type.typcollation` for the expected type. This binds text columns to their type-default collation while naturally requiring zero for non-collatable types. Any mismatch raises the existing fixed structural-schema error before constraint, RLS-policy, or index convergence. Static RED `f39612fd7451fcd2644ad6162467b30cdee43721` pins the catalog comparison. The first container specimen `40d99eaf6afefcf29074f2e092d1bff24880c391` targeted `tenant_scope`, but review rejected it as sufficient executable evidence because PostgreSQL can block that type change on the existing RLS-policy dependency before migration runs. Corrected acceptance `9306e4e12d64ccff3f41101df867f0abadef0e3d` instead changes `evidence_id` to explicit `COLLATE "C"`; this preserves RLS and reaches the migration structural guard, then restores `COLLATE "default"` and requires successful reapplication. Causal source fix `58f774a2621acfeaafe5e144fabfd181872da0cc` adds the guard; `0f2d729910e38b02bef111da05fae7efc285c025` mirrors the exact source blob into the Docker initializer.

**Effect.** A successful migration no longer admits same-type columns with package-undeclared collation semantics. The guarantee is deliberately local: it binds the installed column to the database/type default at migration time; it does not freeze the operating system, ICU implementation, or cluster-wide locale configuration, and it does not protect against a privileged administrator changing schema after validation. Hosted exact-head PostgreSQL execution remains required before GREEN is claimed.

## Integrity decision trace: lifecycle relation durability authority

**Problem.** The outbox is documented and implemented as durable publication intent, but the previous structural admission guard did not inspect `pg_class.relkind` or `relpersistence`. PostgreSQL allows an ordinary table to be converted to `UNLOGGED` while preserving the visible row shape, constraints, RLS policies, and indexes. PostgreSQL 18 documents that unlogged-table data is not written to WAL, is truncated after a crash or unclean shutdown, and is not replicated to standby servers (PostgreSQL Global Development Group, 2026g). A migration could therefore report success while the persistence object no longer satisfied the package's durability claim.

**Constraints.** Fail before later constraint/RLS/index repair on a noncanonical persistence object; preserve package/Docker SQL byte identity; do not infer that a storage rewrite is operationally safe; and do not claim that catalog admission alone proves recovery of publication intent lost during a prior unlogged interval.

**Alternatives.** Treating relation persistence as an operator-only concern was rejected because migration success is used as schema-readiness evidence and the bounded context explicitly owns durable lifecycle intent. Automatically issuing `ALTER TABLE ... SET LOGGED` was rejected because it can rewrite storage, generate WAL, affect availability, and cannot reconstruct rows already lost after an unclean shutdown. Accepting partitioned or other relation kinds by column compatibility was rejected because runtime and migration semantics were reviewed for one ordinary table.

**Decision.** Migration 0008 now requires the canonical `public.llm_context_lifecycle_outbox` object to resolve through `pg_class`/`pg_namespace` as an ordinary table (`relkind = 'r'`) with permanent/logged persistence (`relpersistence = 'p'`) in `public`. Static RED `e47b77aacca38149d5423b4f459531d633dc75c7` pins that catalog contract. Executable specimen `a07e1fd919db7b3bafa098ff6e97a7ce7ba55289` converts a fresh real PostgreSQL outbox to `UNLOGGED`, requires reapplication to fail with the fixed structural-schema error, restores `LOGGED`, and then requires migration success. Causal source fix `47243752a04c2d9a798130116e73e6f1bf5bf59f` adds the admission guard; mirror commit `b12d397ae6ab8ee5039de6052f3fce3aa83e3cff` points the Docker initializer at the same SQL blob `7e4a96e84fc7b54ec6375733b6f08ad6b6161184` without force-pushing the stack.

**Effect.** A successful migration can no longer be used as evidence for a structurally canonical but unlogged lifecycle outbox. The repair is intentionally fail-closed: operators must determine whether any unlogged interval included a crash, reconcile aggregate/publication/receipt state and standby gaps, and only then restore logged persistence. Hosted exact-head PostgreSQL execution remains required before this repair is called GREEN.

## Integrity decision trace: lifecycle CHECK predicate identity

**Problem.** A constraint comment is mutable metadata. The previous canonical payload and timestamp admission guards checked name, CHECK type, validation/inheritance state, and an expected package comment stamp, but did not compare the installed predicate. A restore or manual DDL sequence could therefore install a different same-name predicate and copy the expected comment; migration would then report convergence despite executable grammar drift.

**Constraints.** Detect executable predicate drift without rewriting already-current production constraints on every reapplication. Avoid hard-coding PostgreSQL decompiler formatting that can vary by server version. Preserve package/Docker SQL byte parity and existing data; a mismatch may be repaired by replacing only the package-owned canonical CHECK name. Do not claim protection against a PostgreSQL superuser capable of rewriting both schema and migration authority.

**Alternatives.** Treating the comment stamp as sufficient was rejected because it is not executable identity. Recreating every canonical CHECK on every migration was rejected because it repeats table validation and heavyweight DDL. Comparing against a hand-written `pg_get_expr` string was rejected because PostgreSQL documents `pg_get_expr` as a decompiled reconstruction rather than original SQL text. Comparing a raw `conbin` node tree to a constant was rejected because it would couple migration authority to internal representation details.

**Decision.** Migration 0008 creates one session-local temporary probe table with the reviewed payload, `valid_time`, and `system_time` CHECK definitions, asks the running PostgreSQL version to decompile each probe through `pg_get_expr(conbin, conrelid, false)`, stores those three canonical expressions in PL/pgSQL variables, and drops the probe before touching package-owned durable CHECKs. Each live canonical CHECK is admitted only when catalog kind/validation/inheritance, parsed expression, and review stamp all agree. After a repair, the same predicate identity is verified again before legacy timestamp retirement or later migration work. The TEMP relation is created without a schema-qualified name, as required by PostgreSQL 18, and is referenced afterward through `pg_temp`.

RED `c792f4d5ef8b6ae96106cdc32f0959d718063e10` spoofs the canonical payload name and expected comment on `CHECK (true)`, reapplies migration, then attempts a payload that only the real canonical grammar rejects. The initial predicate-authority fix is `cd97e0b0d3d8c0099e8393d55ba8ebb094a16272`; `d7b4c7879e47db80d69a76af5f5ece1c0de3906d` corrects TEMP creation to PostgreSQL's documented syntax; `89e67fca2cf2fbe0bfc3a1ae39b11315ec73cb7e` restores package/Docker byte identity. Static contracts then bind payload and both timestamp generations to parsed expression identity.

**Effect.** Same-name or same-name/same-comment package CHECK drift no longer qualifies as converged state. Already-current durable constraints avoid replacement DDL; the recurring work is limited to a session-local probe and catalog comparison. This is migration-convergence evidence, not a security boundary against a database superuser or a principal that can replace the reviewed migration bytes. Hosted exact-head PostgreSQL execution remains required before GREEN is claimed.

## Integrity decision trace: lifecycle payload CHECK convergence

**Problem.** Migration 0008 originally put tenant scope, event/evidence identity, digest, and truth-status CHECKs only inside `CREATE TABLE IF NOT EXISTS`. PostgreSQL documents that `IF NOT EXISTS` suppresses the duplicate-relation error but does not guarantee the existing relation resembles the requested definition. A restored, manually repaired, or stale installation could therefore lack one or more payload constraints while the migration continued successfully. A second convergence defect remained after canonical payload v1 was introduced: the ten earlier package-owned CHECKs could coexist with canonical v1. If a restore or operator had changed one predecessor to a stricter predicate, valid current payloads could still be rejected even though canonical v1 was installed successfully.

**Constraints.** Preserve rows accepted by the reviewed current grammar, avoid deleting unknown operator-owned constraints, keep package and Docker SQL byte-identical, and avoid repeated heavyweight DDL after a store has converged. The migration may retire only package-owned predecessor names whose semantics have been superseded by canonical v1.

**Alternatives.** Leaving the predecessor checks in place was rejected because multiple simultaneous package grammar authorities prevent deterministic convergence. Dropping every noncanonical CHECK was rejected because an unknown constraint can encode operator or application invariants outside this migration's authority. Rewriting the table was rejected as unnecessary and more disruptive.

**Decision.** Migration 0008 first establishes and post-verifies `ck_llm_context_lifecycle_outbox_payload_canonical_v1`, including parsed predicate identity, then conditionally drops exactly the ten known pre-canonical package CHECK names. Once absent, ordinary reapplication performs no payload-predecessor DDL. The aggregate v1 remains the package grammar authority; unknown CHECK names are left intact rather than being silently destroyed.

RED `93a9752bf806b41be4aa43c5aa40195da5b9b3cb` pins the required predecessor-retirement order. Causal SQL fix `b32dcd0a89bb831e04980a10728793fe8c3105f2` applies that order to the package and Docker copies with one shared blob. Executable acceptance `eff4efa7a3679a5e94fed6f35f5b2ff3671db50e` uses a real PostgreSQL container, adds a stale package-named `event_type = 'legacy.only'` predecessor after canonical initialization, reapplies migration, and requires that stale predecessor to be gone.

**Effect.** A successful converged migration has one package-owned payload grammar generation instead of canonical v1 plus residual predecessor semantics. The repair does not claim ownership of arbitrary third-party CHECK constraints and does not remove them. Exact-head hosted PostgreSQL execution remains required before GREEN is claimed.

## Reliability/performance decision trace: lifecycle operational-index convergence

**Problem.** Name-only `CREATE INDEX IF NOT EXISTS` does not establish index identity, and even exact `indkey` column numbers do not establish B-tree key semantics. PostgreSQL records per-key collation, operator class, and access-method option bits separately in `pg_index`; `pg_opclass` defines the operator semantics available to an indexed data type. A restored same-name index can therefore keep `(tenant_scope, created_at)` as its physical columns while changing collation, using `text_pattern_ops`, or reversing sort/null ordering (PostgreSQL Global Development Group, 2026i, 2026m).

**Constraints.** Preserve already-current indexes without recurring rebuild DDL, but rebuild a package-owned same-target index once when its executable key semantics differ. Do not accept a name collision on another relation. Derive canonical operator-class identity from the running PostgreSQL catalog rather than hard-coding cluster-local OIDs.

**Alternatives.** Checking only index name and `indkey` was rejected because it misses index-only semantic drift. Comparing only `pg_get_indexdef` text was rejected as a decompiled representation rather than the underlying catalog identity. Hard-coding operator-class OIDs was rejected because OIDs are installation-local.

**Decision.** Migration admits the operational index only when catalog state proves the target relation, `public` namespace, B-tree access method, valid/ready/live nonunique two-key shape, no expression/predicate, exact `(tenant_scope, created_at)` key order, tenant key collation equal to the canonical column collation, zero collation for `created_at`, the default B-tree operator class for `text` and `timestamptz`, and zero/default `indoption` for both keys. Static RED `11238f8c792abcfbfd898d3ff4cb359e417f9b89` pins those fields. PostgreSQL specimen `6af5e30bba8c406ddc3bad11af9bb2b8f651ae7a` recreates the same-name/same-column index with explicit `COLLATE "C"`, `text_pattern_ops`, DESC, and NULLS FIRST. Causal source fix `d3b7dd36760bc3316f860194b7733b371bfe4b2f` adds catalog admission, and `44f782d3abe6f2bc38f0173ca73a8c60796953e9` mirrors the same SQL blob into the Docker initializer.

**Effect.** Successful migration establishes the tenant-first operational index's comparison and ordering semantics rather than merely its name and column numbers. This removes another restore/migration latency and query-plan drift source but does not by itself prove the buyer-path p95 target. Exact-head PostgreSQL execution remains required before GREEN is claimed.

## Release gate

A release is incomplete while any runnable merge, fix, test, restack, review/thread, owner-path, documentation-to-code, or buyer-gap action remains. Before release, perform two fresh live sweeps and require the exact protected head, required checks, review state, security evidence, immutable dependency identities, and release artifacts to agree. Routine status reporting is not completion evidence.
