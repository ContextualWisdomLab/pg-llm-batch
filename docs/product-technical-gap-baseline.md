# Product / Technical Gap Baseline

This document records commercial-development gaps owned by `pg-llm-batch` or materially gating its release. It is a code-current decision/evidence ledger, not a substitute for live PR, check, review, release, or protected-ref reads.

The active Context Fabric consumer-readiness stack retains PostgreSQL-backed durable lifecycle intent, tenant/RLS isolation, replay identity, and provider-neutral `BatchInferencePort` ownership in this repository. Mutable sibling heads are candidate evidence only; production integration may consume compatible immutable released contracts through a pg-owned anti-corruption layer.

## Canonical product boundary

`pg-llm-batch` owns durable/asynchronous LLM batch preparation, token/size accounting, provider-neutral batch lifecycle ports, PostgreSQL persistence, tenant/RLS isolation, recovery evidence, result ingestion, and the local outbox used to commit privacy-minimized lifecycle publication intent with product state.

Provider/model discovery, routing, fallback, and credentials remain outside this bounded context. Context Graph / Context Fabric integration may consume only compatible immutable released contracts. Mutable sibling branches, source copies, and cross-service SQL are not production authority. PR #323 separately owns the commercial PostgreSQL driver migration, including shared database-driver code; this stack does not overwrite that lane.

## Integrity decision trace: lifecycle index operator-class authority

**Problem.** Migration 0009 already rejected expression indexes, partial indexes, and standalone UNIQUE arbiters. It still treated a direct-column nonunique index as non-executable authority. PostgreSQL records each index key's operator class in `pg_index.indclass`; an operator class defines index semantics and support functions for a data type/access-method pair. PostgreSQL's index extension documentation states that index machinery invokes those support functions without checking ordinary execute privileges. A user-defined comparator can therefore raise during index maintenance and reject an otherwise canonical lifecycle event even when `indexprs` and `indpred` are both NULL.

**Constraints.** Preserve ordinary PostgreSQL-core operational indexes, including non-btree methods whose default operator class is built into `pg_catalog`; keep package/Docker migration bytes identical; fail closed before accepting operator-selected support-function authority; do not auto-drop unknown indexes or operator classes; and do not claim protection against a PostgreSQL superuser that can rewrite core catalog authority after validation. The tenant/application contract already excludes superuser and `BYPASSRLS` identities from ordinary application isolation.

**Alternatives.** Treating every plain column index as inert was rejected because operator-class support functions are still invoked by index maintenance. Banning every non-btree index was rejected as broader than the causal boundary: a built-in nonunique hash index using PostgreSQL's default `pg_catalog` operator class does not add operator-selected function authority. Allow-listing function names was rejected because names do not prove body, language, dependency, or ownership identity. Automatically dropping unknown indexes/operator classes was rejected because their operational role and data/performance consequences are not package-owned facts.

**Decision.** For every direct key position, migration 0009 requires the selected `pg_opclass` row to belong to `pg_catalog`, be marked default for the exact indexed table-attribute type, and belong to the same access method as the index relation. Expression/predicate indexes remain rejected. Standalone UNIQUE indexes remain rejected unless `pg_constraint.conindid` proves the exact canonical PK or tenant/evidence replay arbiter. Static RED `b1bca812c34c14262ed644c4122253504bb7e042` established the missing opclass guard. Causal package repair `7c8c6857bb6262c83474587fe620c4f7208d4336`, Docker mirror `06566d0af7f592e85e45cb2a8c565d026bda7d8c`, and static contract `cb1ae3670de5827160143f9f4d0e162108906ae6` bind both migration copies to blob `9920c405ef9e86992c2258a9a413a15e9c8b3a5e`. Executable acceptance `885cbca184093f830f8947e9cd92679234d3e573` first admits a PostgreSQL-core nonunique hash index, then constructs a direct-column btree index whose custom operator-class comparator raises on `batch.lifecycle.blocked`, proves the write rejection, and requires migration 0009 itself to reject that catalog state. ADR 0025 records the full decision and operator boundary.

**Effect.** Successful migration no longer equates `indexprs IS NULL AND indpred IS NULL` with absence of executable index authority. This is migration-time catalog admission, not defense against privileged post-validation catalog mutation. ## Integrity decision trace: lifecycle column collation authority

**Problem.** PostgreSQL records a column's effective collation independently of its data-type OID. ## Integrity decision trace: lifecycle relation durability authority

**Constraints.** Preserve already-current indexes without recurring rebuild DDL, but rebuild a package-owned same-target index once when its executable key semantics differ. Do not accept a name collision on another relation. Derive canonical operator-class identity from the running PostgreSQL catalog rather than hard-coding cluster-local OIDs. A repair must be post-verified with the same predicate used for admission, and package/Docker SQL must remain byte-identical.

**Alternatives.** Checking only index name and `indkey` was rejected because it misses index-only semantic drift. Comparing only `pg_get_indexdef` text was rejected as a decompiled representation rather than the underlying catalog identity. Hard-coding operator-class OIDs was rejected because OIDs are installation-local. Assuming successful `CREATE INDEX` establishes the reviewed final catalog state was rejected because migration success is used as durability/operability evidence and every other repaired authority path already follows converge-then-verify semantics.

**Decision.** Migration admits the operational index only when catalog state proves the target relation, `public` namespace, B-tree access method, valid/ready/live nonunique two-key shape, no expression/predicate, exact `(tenant_scope, created_at)` key order, tenant key collation equal to the canonical column collation, zero collation for `created_at`, the default B-tree operator class for `text` and `timestamptz`, and zero/default `indoption` for both keys. After any repair, migration repeats that exact catalog predicate and raises `lifecycle outbox operational index failed canonical verification` if the installed index is not canonical. Existing semantic REDs are `11238f8c792abcfbfd898d3ff4cb359e417f9b89` and PostgreSQL specimen `6af5e30bba8c406ddc3bad11af9bb2b8f651ae7a`; post-verification RED `4683f4108b36730804e361c7cf697d916064ee62` requires the second catalog read. Source fix `bdbdf5bb7ffdbaef66aee697beda1fefa5d2c2e2` added it, self-review repair `49c7f9511e8607f533f301ac2f78a3d6aa0ca72f` corrected the new opclass catalog join, and mirror `88724fa4521aadf4f5955f0ca831c5aeeb9b4896` restored byte identity on blob `3623f70ae6d371397b43b4deccaccea4087391a1`. Regression `c12e182c15f332eca64823a736a385d9cba0c02e` requires the admission and verifier predicates to remain text-identical. The wired PostgreSQL acceptance lineage `21cdec60cfc97ad273b34a7829d77ebddd4633b4` → `232f8a478ff1d4cad773105295013fcb48e04c5a` → `cf841881f9f93c3f263f61baf0d7943416deceb1` uses a test event trigger to rename the just-created index, emits a server-log marker only after the rename completes, requires migration failure/rollback, removes the test trigger, and requires successful canonical reapplication.

**Effect.** Successful migration now establishes and re-verifies the tenant-first operational index's comparison and ordering semantics rather than merely its name, columns, or successful DDL return. This removes another restore/migration latency and query-plan drift source but does not by itself prove the buyer-path p95 target. Exact-head PostgreSQL execution remains required before GREEN is claimed.

## Release gate

A release is incomplete while any runnable merge, fix, test, restack, review/thread, owner-path, documentation-to-code, or buyer-gap action remains. Before release, perform two fresh live sweeps and require the exact protected head, required checks, review state, security evidence, immutable dependency identities, and release artifacts to agree. Routine status reporting is not completion evidence.
